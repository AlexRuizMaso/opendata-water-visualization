\chapter{Requisits del sistema}
\label{Ch:Requirements}

\section{Requisits funcionals}

Els requisits funcionals descriuen les funcionalitats específiques que el sistema ha de proporcionar per a satisfer les necessitats dels usuaris i els objectius del projecte. Aquests requisits es classifiquen per prioritat (Alta, Mitjana, Baixa) i es poden agrupar segons la seva naturalesa.

\begin{itemize}
    \item \textbf{RF-1 (Alta):} Extracció automàtica de dades des de les APIs públiques de la Generalitat de Catalunya. El sistema ha de poder obtenir les dades més recents dels embassaments (nivells, volums i cotes) i de les estacions meteorològiques (precipitació) de forma periòdica sense intervenció manual.
    
    \item \textbf{RF-2 (Alta):} Transformació i neteja de les dades extretes. Les dades obtingudes de les APIs han de ser processades per eliminar inconsistències, convertir unitats quan sigui necessari, i estructurar-les en un format adequat per a la seva posterior visualització i anàlisi.
    
    \item \textbf{RF-3 (Alta):} Emmagatzematge de dades processades en format JSON versionat. Les dades transformades han de ser desades a fitxers JSON amb timestamps per permetre l'historial de dades i facilitar el control de versions a través de Git.
    
    \item \textbf{RF-4 (Alta):} Desenvolupament d'una interfície web interactiva amb quatre panells de visualització diferenciats:
    \begin{itemize}
        \item Panell 1: Mapa interactiu que mostri la ubicació dels embassaments i estacions meteorològiques amb indicadors en temps real
        \item Panell 2: Evolució temporal dels nivells d'embassaments amb controls de filtratge per període de temps
        \item Panell 3: Anàlisi de correlació entre dades de precipitació i nivells d'embassaments
        \item Panell 4: Matriu d'alertes de sequera amb indicadors semàfor basats en percentatge d'ocupació
    \end{itemize}
    
    \item \textbf{RF-5 (Mitjana):} Implementació de lògica de detecció automàtica de sequera. El sistema ha de calcular indicadors de risc basats en llindars predefinits de percentatge d'ocupació dels embassaments (crític <20\%, avís 20-50\%, normal 50-75\%, òptim >75\%) i generar alertes quan es superin els límits establerts.
    
    \item \textbf{RF-6 (Mitjana):} Automatització de l'actualització de dades via GitHub Actions. El pipeline ETL ha de ser programat per executar-se de forma automàtica a una hora específica cada dia, assegurant que les dades disponibles al frontend siguin sempre les més recents possibles.
\end{itemize}

\section{Requisits no funcionals}

Els requisits no funcionals definen les característiques de qualitat, restriccions i condicions que el sistema ha de complir, però que no es relacionen directament amb funcions específiques. Aquests requisits afecten a l'arquitectura general, el rendiment, l'usabilitat i altres aspects del sistema.

\begin{itemize}
    \item \textbf{RNF-1 (Alta): Rendiment.} El sistema ha de ser capaç de processar més de 200.000 registres de dades en total (~87.000 d'embassaments i ~135.000 de precipitació) utilitzant paginació de 50.000 registres per petició a l'API, en un termini inferior als 5 minuts durant l'execució del pipeline ETL. La interfície web ha de carregar i mostrar les dades en menys de 3 segons per a una experiència d'usuari satisfactòria. \textit{En termes tècnics, això implica optimitzar les peticions HTTP (la biblioteca axios permet gestió eficient de connexions), minimitzar el processament redundant al pipeline, i utilitzar tècniques de caché i minificació al frontend (Vite proporciona minificació automàtica del codi JavaScript).}
    
    \item \textbf{RNF-2 (Alta): Usabilitat.} La interfície ha de ser intuïtiva i accessible per a usuaris amb diversos nivells de competència tècnica, des de professionals del sector fins a ciutadans interessats en el tema. Això inclou navegació clara, etiquetatge comprensible, i elements interactius que siguin fàcils d'entendre i utilitzar. \textit{React (framework utilitzat) permet crear interfícies reactives que responen immediatament a les accions de l'usuari, mentre que React Router gestiona la navegació entre pàgines de forma fluida sense recarregar tot el contingut.}
    
    \item \textbf{RNF-3 (Alta): Seguretat.} Tot accés a recursos externs (APIs públiques) ha de realitzar-se mitjançant connexions segures (HTTPS). No s'emmagatzena cap informació sensible com contrasenyes o tokens en el repositori, utilitzant mecanismes com fitxers d'entorn (\texttt{.env}) per a la configuració quan sigui necessari. \textit{El protocol HTTPS xifra les comunicacions entre el servidor i el client, assegurant que les dades intercanviades no siguin interceptades. El fitxer .env permet separar la configuració sensible del codi font, evitant que informació privada es public accidentalment.}
    
    \item \textbf{RNF-4 (Mitjana): Portabilitat.} El sistema ha de ser desplegable a diferents plataformes d'hosting sense modificacions significatives al codi, incloent opcions gratuïtes o de baix cost com GitHub Pages, Vercel o Netlify per al frontend, i la capacitat d'executar l'ETL en qualsevol entorn que suporti Node.js. \textit{El frontend és una aplicació estàtica (HTML, CSS, JavaScript) que pot ser servida per qualsevol servidor web sense necessitat de backend. L'ETL és un script Node.js que pot executar-se en qualsevol ordinador o servidor amb Node.js instal·lat.}
    
    \item \textbf{RNF-5 (Mitjana): Mantenibilitat.} El codi font ha de seguir convencions establertes, estar ben documentat, i utilitzar una estructura modular que faciliti la comprensió, modificació i ampliació futura del sistema. Això inclou comentaris adequats, noms de variables i funcions significatius, i separació clara de responsabilitats entre components. \textit{Una estructura modular significa que cada funcionalitat està separada en fitxers independents que es poden modificar sense afectar la resta del sistema. Les convencions de nomenclatura fan que qualsevol desenvolupador pugui entendre ràpidament la funció de cada variable o funció.}
    
    \item \textbf{RNF-6 (Baixa): Escalabilitat.} Mentre que el volum inicial de dades és gestionable, l'arquitectura ha de permetre un augment futur del volum de dades o l'addició de nous tipus de dades sense requerir un redisseny complet del sistema. \textit{La separació clara entre el pipeline ETL (que processa les dades) i el frontend (que les mostra) permet augmentar el volum de dades sense modificar la interfície, o afegir nous panells de visualització sense canviar el pipeline.}
\end{itemize}
